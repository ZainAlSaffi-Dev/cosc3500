## Notes from run 568325

- The harness printed 29 days until Judgement Day on 2026-08-26, so the grading run is near 2026-09-24. Confirm the submission due date on Blackboard.
- Debug jobs land on whatever cosc3500 node is free, and the pool is heterogeneous. So far it has produced vcpu-4 and a100-a (both AMD EPYC 7542, Zen 2) and r730-0 (Intel Xeon E5-2670 v3, Haswell). Ratios from different nodes are not comparable, always read the CPU line in the output.
- Run 568373 printed hostname a100-a with host CPU AMD EPYC 7542. That resolves MASTERDOC Appendix D item 1, the graded nodes' host CPU is Zen 2 with AVX2 and FMA, so MKL runs an AVX2+FMA path while our code is capped at AVX1 without FMA.
- The librubric.so reference is Fortran-order MKL cgemm with 'N','N' transpose flags, confirmed by disassembly. The buffers are column-major as far as the grader is concerned. Row-major code must compute B*A to match. Run 568373 (error 2.6e+02) versus run 568381 (error 2.3e-08) is the empirical confirmation.
- Phase 2 GFLOP/s accounting from run 568424 on r730-0. Ours at 2.057 matrices/s is 141 GFLOP/s (68.7 GFLOP per 4M multiply). The AVX1 no-FMA ceiling at the 2.3GHz base clock is 147 GFLOP/s on 4 cores, so the kernel runs at roughly 96 percent of the base-clock ceiling (turbo raises the true ceiling somewhat). MKL measured 158 GFLOP/s on this Haswell node. On the graded Zen 2 nodes both sides change, MKL gets a faster FMA path but Zen 2 can also dual-issue our separate mul and add at 32 flops per cycle, so the graded ratio needs its own measurement.
- Recalibration from run 568383 on r730-0. MKL at 2.307 matrices/s is about 158 GFLOP/s (68.7 GFLOP per 4M multiply), our baseline at 0.281/s is about 19 GFLOP/s, roughly 13 percent of the 147 GFLOP/s AVX1 no-FMA ceiling on that node (4 cores at 2.3GHz times 16 flops per cycle). The 8.2 ratio beat the 15-25 estimate, most likely because g++ auto-vectorised the contiguous inner j loop. Caution, r730-0 is a slow Haswell node. The graded a100 nodes are EPYC 7542, where MKL will be faster and the ratio likely worse. A bench run that lands on an EPYC node is needed before trusting any ratio against the marking thresholds.
- MKL reference at N=128 on vcpu-4 was 10116.686 matrices/second, about 0.1 ms per multiply. Too small to project N=2048 from, the 256MiB rep pool and cache behaviour differ entirely at graded size.
- GPU transfer question (MASTERDOC Appendix D item 2), resolved by run 568780. Fitting time = a·N² + b·N³ to the register-kernel runs at 1024, 2048 and 4096 gives an N² share of only about 0.7 ms at N=2048 against a 5.9 ms total. 100 MB of per-rep PCIe copies would need 4 ms or more on any PCIe4 link, so the harness GPU buffers cannot be ordinary host memory, they must already be device-resident or mapped (managed allocation inside librubric). Per-rep transfers are therefore nearly free for us and for the cuBLAS reference alike, rung G4 (pinning, stream overlap) buys nothing, and the remaining gap to the reference is pure kernel arithmetic. Implied rates at N=2048, ours about 13 TFLOP/s, cuBLAS about 15 TFLOP/s, against a 19.5 TFLOP/s FP32 ceiling.
- GPU error is 3.228e-08 at N=2048 in every configuration, three times under tolerance. All three kernels accumulate k in the same ascending order, so the error is a property of the summation depth, not the kernel choice.
- MPI interconnect question (MASTERDOC Appendix D item 3), resolved by run 568790. The two-node time of 0.1487 s per multiply is almost exactly half the single-node CPU time of 0.240 s plus a few milliseconds, so the 16.8 MB per-rank allgather costs single-digit milliseconds. The a100 pair interconnect is fast enough that the plain blocking MPI_Allgatherv fits the 0.6 line with room, and the chunked Iallgatherv pipelining from the plan is unnecessary.
- The 568790 job was scheduled onto a100-a and a100-b, the same pinned pair JudgementDay uses, so the 0.496 MPI ratio is already a graded-hardware number.
